# ADR-006: Migration baseline — handwritten raw-SQL Alembic, bootstrap-stamped

- **Status:** Accepted (2026-11-06)
- **Deciders:** mir-ashiq
- **Supersedes:** —

## Context

`db/schema.sql` + `db/functions.sql` are the v0.x bootstrap: applied wholesale by `python -m ledgerforge.bootstrap` (CLI, Docker entrypoint, tests), deliberately idempotent. Two problems as the project approaches 1.0:

1. There is no versioned history of schema changes — operators cannot see what changed between releases, and an in-place upgrade path does not exist.
2. The roadmap needs one before the first post-1.0 schema change (multi-currency FX tables, the `periods` table) so those changes ship as migrations instead of informal `psql` scripts.

The obvious default — SQLAlchemy metadata + Alembic autogenerate — does not fit this schema: Laws 1 and 2 are enforced in the database itself (trigger functions, a `DEFERRABLE INITIALLY DEFERRED` constraint trigger, `BEFORE UPDATE/DELETE` mutation blockers), plus a partial unique index, a GIN/trigram index, an application role with least-privilege grants, and the `rpt` schema of SQL functions. Alembic autogenerate diffs tables/columns/indexes/FKs against ORM metadata and is blind to all of that — an autogenerated baseline would silently omit the financial-law enforcement.

## Decision

1. **Handwritten raw-SQL revisions.** Every migration is a plain SQL script executed via `op.execute()` (psycopg runs multi-statement scripts, including `$$`-quoted bodies, in one call). Autogenerate is banned: the schema's most important parts are invisible to it. Revision ids are short and sortable (`0002_add_periods`); the template says so.

2. **One baseline revision, embedded verbatim.** `db/migrations/versions/0001_baseline.py` embeds `schema.sql` + `functions.sql` byte-for-byte (`scripts/regen_baseline.py` regenerates it; `--check` is a CI step). Seed data (the chart of accounts) is *not* part of any migration — it is data, not schema, and remains the bootstrap's job.

3. **The drift guard makes drift impossible to merge.** `tests/test_migrations.py` provisions one database via `alembic upgrade head` and one via the SQL bootstrap, then compares structural fingerprints taken from the catalogs (schemas, extensions, tables/columns with types/defaults/identity, index definitions, constraint definitions, trigger definitions, function definitions, and the `ledgerforge_app` grants). Any difference fails CI with a unified diff. No `pg_dump`/client-version coupling; runs on pgserver and CI PostgreSQL alike.

4. **The bootstrap stamps the version table.** After applying the SQL files (which *are* the flattened head state), `ledgerforge.migrations.stamp_schema()` writes the current head into `alembic_version`. Databases provisioned either way converge; a later `alembic upgrade head` on a bootstrapped database is a no-op, never a re-run. `python -m ledgerforge.migrations` exposes upgrade/downgrade/stamp/current from any install (the wheel ships the tree under `ledgerforge/sql/migrations`).

5. **Pre-1.0 vs post-1.0 policy.** Until 1.0 (no deployments to preserve): schema changes land in the SQL files first, then `make baseline-regen` re-embeds them — alpha users re-bootstrap. After 1.0 the baseline freezes; a schema change ships as a *new* revision that also updates the SQL files in the same PR, and the drift guard proves the two stay identical. New revisions carry their own `GRANT`s to `ledgerforge_app` (the blanket `ON ALL TABLES` in `schema.sql` only covers tables existing at bootstrap time).

## Consequences

- **(+)** The first post-1.0 schema change can ship as `0002_*` with nothing else to invent; the upgrade path exists today, proven by tests (`upgrade`, `downgrade`, both interplay orders).
- **(+)** Law enforcement (triggers, functions, grants) is captured exactly — it *is* the SQL that already enforces it.
- **(+)** Operators keep the dead-simple SQL bootstrap; adoption of migrations is `make migrate-stamp`, zero re-runs.
- **(−)** Migrations are handwritten, not autogenerated — accepted, since autogenerate cannot see the parts that matter (that is the point).
- **(−)** Two copies of the schema exist pre-1.0 (SQL files + embedded baseline) — mitigated to zero by the regen script and the CI drift guard.
- **(−)** Downgrade of the baseline is destructive by definition; it drops tables, the `rpt` schema and trigger functions, revokes everything from `ledgerforge_app` and drops the role best-effort. `pg_trgm` is deliberately left in place (created `IF NOT EXISTS`, so it may predate the migration and be shared). Neither survives 1.0 as a surprise: both are documented in the revision itself.
